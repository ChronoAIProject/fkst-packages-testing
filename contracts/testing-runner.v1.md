# testing-runner.v1

`testing-runner` is the adapter boundary between fkst testing events and concrete testing execution backends.

## Request queues

- `testing-runner.module_test_request`
  - `schema`: `testing-runner.module-test-loop.request.v1`
  - required: `module`
  - optional: `backend`, `config`, `e2e_driver`, `no_browser`, `dry_run`, `dry_run_github`, `native_argv`, `ui_loop`, `module_discovery`, `cdp_execution`, `preflight_result`, `artifact_root`, `source_ref`, `trace_id`, `dedup_key`
- `testing-runner.platform_test_request`
  - `schema`: `testing-runner.platform-test-loop.request.v1`
  - optional: `backend`, `modules`, `priority`, `config`, `e2e_driver`, `no_browser`, `dry_run`, `dry_run_github`, `preflight_result`, `artifact_root`, `source_ref`, `trace_id`, `dedup_key`
- `testing-runner.online_regression_request`
  - `schema`: `testing-runner.online-regression.request.v1`
  - optional: `backend`, `config`, `driver`, `heartbeat_url`, `final_summary`, `no_browser`, `dry_run`, `dry_run_github`, `preflight_result`, `artifact_root`, `source_ref`, `trace_id`, `dedup_key`

`backend` defaults to `fkst-native`, which is the only executable runtime backend. `agentic-testing-cli` is accepted only as blocked legacy compatibility and must never construct or invoke the old Python runner. `agentic_testing_repo_root` is not an active request field.

`preflight_result` is optional small status metadata from an upstream readiness gate. For `fkst-native`, any provided preflight status other than `ready` must return `blocked` before native execution planning.

When `preflight_result` comes from `browser-readiness.result.v1`, it may include a bounded `request_context` copied from the original readiness check. This context is only for restoring host-provided execution intent after readiness gating. Supported fields are `native_argv`, `dry_run`, and `no_browser`; unknown fields must be rejected by the readiness package. `request_context` must remain small control metadata and must not carry reports, evidence bodies, browser state, credentials, cookies, or tokens.

`native_argv` is optional for module requests only and is a bounded argument vector for native module execution. When present with `backend = "fkst-native"`, `dry_run = false`, and either `no_browser = true` or `e2e_driver` is present, it may be executed directly by the native adapter. It must not target the legacy `agentic-testing` CLI or host wrapper.

`ui_loop` is optional for module requests only and is the FKST-native module UI loop control envelope. It may contain only small control fields: required `base_url` and non-empty `allowed_origins`; optional `browser_readiness_ref`, `cdp_readiness_ref`, `artifact_root`, `dry_run`, `priority`, `mutation_policy`, `gap_ref`, and `backlog_ref`. `allowed_origins` and `priority` are dense bounded lists of at most 16 items. `mutation_policy` is `read-only`, `dry-run`, or `host-approved`. Pointer fields must be bounded strings and `artifact_root`, when present inside `ui_loop`, must also be a safe `.testing/runs/...` path. Unknown `ui_loop` fields are malformed; inline screenshots, traces, browser storage, credentials, cookies, tokens, report bodies, or browser state must not be accepted.

`module_discovery` is optional for module requests only and uses `testing-runner.module-discovery.v1`. It requires the existing `ui_loop` scope for `base_url` and `allowed_origins`; it must not redefine runtime scope. It may contain optional bounded `observations` and `limitations`. Observations are host- or discovery-supplied deterministic route, navigation, accessibility-visible, browser, or browser-visible facts with bounded `id`/`name`, `entry_url`, visible label or route, discovery source, confidence, and `evidence_pointer`. Supported discovery sources are `route`, `route-manifest`, `navigation`, `nav-link`, `accessibility`, `a11y-visible`, `browser`, and `browser-visible`. Unknown fields and inline browser state, screenshots, traces, credentials, cookies, tokens, or report bodies are malformed.

`cdp_execution` is optional for module requests only and uses `testing-runner.module-cdp-execution.v1`. It requires the existing `ui_loop` scope and never redefines runtime scope. It may contain only bounded controller fields: optional integer `step_budget` from 1 to 32, optional dense `case_priorities` containing `P0`/`P1`/`P2`, optional dense `stop_conditions`, optional bounded `mutation_fixtures`, and optional `ai_generation`. Mutation fixtures are small pointer-only records keyed by `case_id`; they may describe only `create-test-data` or `edit-test-data` safe local fixtures, or default-blocked risk kinds (`delete`, `permissions`, `billing`, `external-notification`, `real-user-impact`). Safe mutation execution requires `ui_loop.mutation_policy` other than `read-only`, a fixture pointer, evidence pointer, and cleanup or rollback pointer; otherwise the P2 case remains a fixture/data gap and is not executed. The controller reuses an already-ready local browser/CDP session reported by readiness; it must not perform credential login, MFA, CAPTCHA handling, destructive changes, externally visible mutations, or real-user-impacting actions. Unknown fields and inline screenshots, traces, browser storage, credentials, cookies, tokens, report bodies, or browser state are malformed.

`cdp_execution.ai_generation` uses `testing-runner.ai-case-generation.request.v1`. Supported modes are `disabled` and `autonomous-reviewed`; only `autonomous-reviewed` may enter the AI authoring and review loop. The request may set a bounded `case_budget`, bounded `allowed_case_kinds`, bounded `allowed_action_kinds`, and safe artifact pointers for `context_manifest_path`, `generated_cases_path`, `generated_case_gate_path`, `ai_agent_generation_path`, `generated_case_agent_review_path`, and `ai_test_design_loop_path`. If these pointers are omitted, the runner derives them under the module `artifact_root`. Inline generated cases, inline model transcripts, raw prompts/responses, screenshots, browser storage, credentials, cookies, tokens, report bodies, and browser state are malformed; generated cases and reviews move only through artifact pointers plus digest binding.

The autonomous-reviewed AI loop is fail-closed. The pipeline writes a sanitized `testing-runner.ai-context-manifest.v1`, invokes a read-only AI author for `testing-runner.ai-case-candidates.v1`, canonicalizes candidates into `testing-runner.generated-test-cases.v1`, submits the generated artifact for consensus review, runs deterministic schema/scope gating into `testing-runner.generated-case-gate.v1`, submits executable candidates for a second consensus gate, and only then resumes module execution with pointer fields populated. Both consensus approvals require complete approve evidence from the configured consensus angles; reject, converge, unavailable, stale, malformed, or missing artifacts produce a blocked testing result before generated-case execution. If a positive `case_budget` produces zero generated cases, the AI design loop is `degraded`, not `reviewed`.

`artifact_root`, when provided, must be a safe relative path under `.testing/runs/...`; paths outside that prefix, parent traversal, NUL bytes, or empty values are malformed. If omitted, the runner derives a safe `.testing/runs/...` pointer from request identity fields.

`trace_id` and `dedup_key`, when provided, must be bounded strings. `trace_id` identifies one logical testing trace across runner, artifacts, and publication. `dedup_key` is the stable idempotency key that downstream write boundaries can use to collapse replays. If omitted, packages derive deterministic generic values from stable source/artifact fields; timestamps, randomness, product names, and host-specific defaults must not be used.

## Host-owned native module profiles

A native module profile is downstream-owned configuration, not a new fkst event schema. A host profile may translate each module entry into the existing readiness and module-start events with these neutral fields:

- `module`: bounded logical module identifier.
- `ui_loop`: local runtime scope, allowed origins, readiness refs, and mutation policy.
- `module_discovery`: bounded host-owned route/navigation/accessibility facts with evidence pointers.
- `cdp_execution`: bounded native execution controls for already-ready local browser/CDP sessions.
- `native_argv`: optional dense argv list only for narrow host-owned no-browser or browser-driver checks; it must not target legacy `agentic-testing` runners.
- `artifact_root`: safe `.testing/runs/...` path for that module's result metadata and evidence artifacts.
- `trace_id`: bounded logical trace identifier.
- `dedup_key`: bounded stable idempotency key for that module handoff.
- `source_ref`: optional bounded source reference; generic examples default to `{ kind = "host-module", ref = module }`.

The preferred native UI posture is `backend = "fkst-native"`, `dry_run = false`, `ui_loop`, `module_discovery`, and `cdp_execution`. If readiness gating is used, `browser-readiness.result.v1.request_context` may carry only `native_argv`, `dry_run`, and `no_browser`; later lifecycle packages restore those fields from the preflight result. Product module names, product URLs, host environment variable names, credentials, browser state, large reports, and publication destinations belong in the downstream host repository, not in this package set.

## Result queue

All request types emit `testing-runner.testing_result` with:

- `schema`: `testing-runner.result.v1`
- `job`: `module-test-loop`, `platform-test-loop`, or `online-regression`
- `status`: `planned`, `passed`, `failed`, `blocked`, or `degraded`
- `artifact_root`: stable pointer under `.testing/runs/...`
- `source_ref`: bounded source reference
- `trace_id`: bounded logical trace identifier
- `dedup_key`: bounded stable idempotency key
- `adapter`: bounded adapter metadata, including `name`; `fkst-native` uses small capability/mode fields and must not include synthesized legacy command strings.

`fkst-native` writes `.testing/runs/.../metadata.json` with schema `testing-runner.native-metadata.v1` for native results. Metadata includes `job`, `status`, `artifact_root`, `source_ref`, `trace_id`, `dedup_key`, bounded `adapter` metadata, and optional `native_summary`. Artifact write failure must return a `blocked` result with an `artifact write failed` stderr excerpt.

`fkst-native` metadata may include `native_summary` for implemented native paths. Online heartbeat summaries use `testing-runner.online-heartbeat-summary.v1`, include only small status fields and a sanitized `target` without query or fragment text. Module no-browser summaries use `testing-runner.module-no-browser-summary.v1`, include only the module name, mode, and status. Module UI loop summaries use `testing-runner.module-ui-loop-summary.v1`, include only module, status, classification, mode, `artifact_root`, `metadata_path`, optional `evidence_bundle_path`, optional `gap_backlog_path`, optional `outcome_classification`, optional `stage_report_path`, optional `issue_drafts_path`, optional `publication_dry_run`, and optional bounded `gap_ref`/`backlog_ref`; they must not embed screenshots, traces, browser state, credentials, cookies, tokens, or inline report data. Module inventory summaries use `testing-runner.module-inventory-summary.v1`, include only module, status, discovery status, `artifact_root`, `inventory_path`, optional `feature_inventory_path`/`test_plan_path`/`plan_status`, optional `evidence_bundle_path`, optional `gap_backlog_path`, optional `outcome_classification`, optional `stage_report_path`, optional `issue_drafts_path`, optional `publication_dry_run`, `module_count`, and `coverage`; detailed module inventory, feature inventory, test plan cases, and evidence pointers stay in `<artifact_root>/module-inventory.json`, `<artifact_root>/feature-inventory.json`, and `<artifact_root>/test-plan.json`. Module CDP execution summaries use `testing-runner.module-cdp-execution-summary.v1`, include only module, status, execution status, classification, mode, `artifact_root`, `execution_path`, `metadata_path`, optional `test_plan_path`/`cdp_readiness_ref`, optional `evidence_bundle_path`, optional `gap_backlog_path`, optional `outcome_classification`, optional `stage_report_path`, optional `issue_drafts_path`, optional `publication_dry_run`, and `action_count`; detailed actions and evidence pointers stay in `<artifact_root>/cdp-execution.json`. When present, `evidence_bundle_path` must equal `<artifact_root>/evidence-bundle.json`, `gap_backlog_path` must equal `<artifact_root>/gap-backlog.json`, and `outcome_classification` must be one of `product-defect`, `harness-tooling-issue`, `environment-session-issue`, `data-fixture-gap`, or `not-executed-risk`. Browser driver summaries use `testing-runner.browser-driver-summary.v1`, include only module, driver, mode, status, and optional bounded readiness audit fields (`status` plus per-session role/status). Missing browser `native_argv` produces a `planned` readiness-gated plan; provided browser `native_argv` runs directly through `fkst-native` and maps exit code `0` to `passed`, non-zero/unavailable execution to `failed`.

For module no-browser native execution, the executable path is intentionally narrow: `backend = "fkst-native"`, `dry_run = false`, `no_browser = true`, a module request, and bounded `native_argv`. Exit code `0` maps to `passed`; any non-zero, missing, or unavailable execution result maps to `failed` with a bounded `stderr_excerpt`. A native module request with `no_browser = true` and no `native_argv` returns `planned` instead of executing. A `native_argv` targeting the legacy `agentic-testing` CLI or host wrapper returns `blocked` before execution.

For native module UI loop requests, the current FKST-native path accepts the contract envelope and can execute bounded CDP-plan slices when `cdp_execution` is present. With `backend = "fkst-native"`, `dry_run = false`, a module request, and `ui_loop`, unsafe runtime input returns a normal `blocked` runner result before exploration. Runtime input is unsafe when `base_url` is not local HTTP or the exact origin is not present in `allowed_origins`. Safe runtime input without `cdp_execution` returns `degraded` with adapter mode `module-ui-loop-contract`, classification `browser-exploration-deferred`, and `testing-runner.module-ui-loop-summary.v1` metadata. Unsafe runtime input returns `blocked` with adapter mode `module-ui-loop-blocked`, classification `unsafe-runtime-input`, and the same pointer-only summary shape. For UI loop summary shapes, the runner writes `<artifact_root>/evidence-bundle.json`, `<artifact_root>/gap-backlog.json`, plus bounded section artifacts under `<artifact_root>/evidence/`; the result and metadata carry only `evidence_bundle_path`, `gap_backlog_path`, and `outcome_classification`. A `native_argv` targeting the legacy `agentic-testing` CLI or host wrapper returns `blocked` before any UI loop handling; the native UI loop path must not fall back to legacy code.

Outcome classification is a bounded native UI-loop diagnostic. Harness/CDP uncertainty, deferred exploration, missing executable plan cases, and step-budget exhaustion classify as `harness-tooling-issue` rather than product defects. Missing local server, login/session, reused CDP session, or readiness inputs classify as `environment-session-issue`. Missing safe fixture, fixture evidence, cleanup pointer, rollback pointer, or safe data classifies as `data-fixture-gap`; explicit reviewed risk left unexecuted classifies as `not-executed-risk`. `product-defect` is allowed only when a native artifact carries supporting evidence and reproducible user-facing behavior; otherwise harness uncertainty must keep the outcome out of product-defect classification. The gap backlog artifact summarizes blocked modules, skipped cases, and required follow-up, but FKST events carry only the backlog pointer and classification.

When `module_discovery` is present, `fkst-native` writes `<artifact_root>/module-inventory.json` with schema `testing-runner.module-inventory.v1` before writing metadata. The inventory records `artifact_kind = "module-inventory"`, sanitized `base_url`, `allowed_origins`, accepted modules, `module_count`, limitations, readiness audit, and provenance. Each accepted module includes `id`, `name`, sanitized `entry_url`, visible label or route, `discovery_source`, `confidence`, and `evidence_pointer`. Discovery is deterministic and bounded to configured `ui_loop` scope; accepted sources include `browser` and `browser-visible` when a generic discovery layer supplies bounded browser facts. URL query and fragment details are stripped from persisted inventory URLs. Missing or blocked readiness produces a blocked/degraded runner result and degraded inventory rather than a product defect. The native evidence bundle includes discovery, planning, skipped-case, failure, console/network, screenshot-index, DOM/state-summary, and action-trace section pointers; section files may contain bounded sanitized URLs, observations, action traces, skipped case reasons, and artifact pointers, but FKST events carry only the bundle pointer. The native gap backlog is a separate `<artifact_root>/gap-backlog.json` artifact with bounded blocked-module, skipped-case, and follow-up records; FKST events must not embed those records. Native UI loop runs also write a human-readable `<artifact_root>/stage-report.md` and dry-run-only `<artifact_root>/issue-drafts.json`; these artifacts may summarize discovered modules, coverage status, executed and skipped user-facing scenarios, classifications, evidence pointers, and issue-draft recommendations, but FKST events carry only the report/draft pointers plus `publication_dry_run = true`.

The same native module discovery path writes `<artifact_root>/feature-inventory.json` with schema `testing-runner.feature-inventory.v1` and `<artifact_root>/test-plan.json` with schema `testing-runner.module-test-plan.v1`. Feature inventory is derived only from accepted module inventory entries and records bounded feature signals plus evidence pointers. The test plan contains P0 entry-health cases for reachability, page loading, key visible elements, and obvious console/network health; P1 low-risk interaction cases for navigation, search/filtering, and opening details when visible; and P2 mutation/edge/negative cases as planned work. The review gate marks cases `executable`, `blocked`, or `not-executed-risk` with bounded reasons. `read-only` mutation policy records P2 write/state changes as not-executed-risk. `dry-run` or `host-approved` may mark only safe local create/edit test-data P2 cases executable, and only when fixture, evidence, and cleanup or rollback pointers are present; missing evidence is a fixture/data gap, while delete, permission, billing, external-notification, and real-user-impact cases remain blocked by default. The native summary remains pointer-only and must not embed module lists, feature inventory bodies, test cases, screenshots, traces, browser state, credentials, cookies, tokens, or report bodies.

When `cdp_execution` is present with safe `ui_loop` input, `fkst-native` writes `<artifact_root>/cdp-execution.json` with schema `testing-runner.module-cdp-execution-result.v1`. The artifact records `artifact_kind = "module-cdp-execution"`, execution status, harness classification, sanitized scope, selected priorities, stop conditions, action count, and bounded action records containing intent, action, target, sanitized URL, observation, and evidence pointer. It may execute only executable selected plan cases, within `allowed_origins`, the module base path, and `step_budget`. Approved generated cases are merged into the deterministic module test plan only after deterministic gate and agent review approve them; multi-step generated cases are expanded into ordered bounded CDP action records, and each generated action consumes `step_budget`. P2 mutation actions execute only as safe local create/edit test-data fixture steps with fixture evidence plus cleanup or rollback pointers recorded in `cdp-execution.json` and repeated only in evidence section artifacts, never in summaries or metadata control fields. Destructive or externally visible P2 cases and missing fixture evidence are blocked or not-executed-risk harness gaps, not product defects. Missing reused CDP session or missing test plan returns `blocked`; exhausted step budget or no executable safe cases returns `degraded`; these are harness classifications, not product defects. The runner also writes the module inventory, feature inventory, test plan, AI context/gate/review artifacts when present, and evidence bundle artifacts when `module_discovery` is present. Metadata remains pointer-only and must not embed actions, mutation fixture details, screenshots, traces, browser state, credentials, cookies, tokens, or report bodies.

For native browser driver execution, the executable path is intentionally host-supplied and bounded: `backend = "fkst-native"`, `dry_run = false`, a module request, `e2e_driver`, and bounded `native_argv`. Readiness details are copied only as a small audit summary. Missing browser `native_argv` returns `planned`; a `native_argv` targeting the legacy `agentic-testing` CLI or host wrapper returns `blocked` before execution.

For online regression, native no-browser execution is only the HTTP heartbeat path with `heartbeat_url`; unsupported native live paths return `blocked` and must not fall back to legacy code.

`fkst-native` must not construct or invoke `agentic_testing.cli` or the legacy `agentic-testing` host wrapper. `agentic_testing_repo_root` is not an active request field.

Payloads must carry small control fields and artifact pointers only; large report bodies, browser storage, credentials, cookies, and tokens stay outside fkst events.

Structured headless API/CLI execution uses the independent
`testing-runner.structured_execution_request` seam and contracts documented in
`structured-execution.v1.md`. It does not extend legacy module `native_argv` authority: every plan
requires a separate authenticated approval bound to the plan digest and exact positive capabilities.
